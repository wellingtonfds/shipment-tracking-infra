# ADR-002 — Modelo de compute com EKS, HPA e distribuição Multi-AZ

## Status

Aceito — 2026-09-24

## Contexto

A plataforma de rastreamento executa uma API HTTP e workers assíncronos com
perfis de carga diferentes. A API recebe consultas e atualizações em horário de
pico, enquanto os workers processam filas, outbox, retentativas e DLQ. Esses
componentes precisam escalar de forma independente e manter disponibilidade
durante falhas pontuais de pods, nós ou zonas de disponibilidade.

A ADR-001 definiu Kubernetes gerenciado por Amazon EKS como base de execução da
plataforma. Esta decisão detalha o modelo de compute adotado para cumprir essa
escolha: node group EKS em subnets privadas, distribuição entre zonas de
disponibilidade e HPAs por workload.

## Decisão

Adotar o **Amazon EKS com managed node group**, workloads distribuídos entre
zonas de disponibilidade e **Horizontal Pod Autoscaler (HPA)** independente
para API e worker.

O Terraform deste repositório entrega a base de infraestrutura necessária para
esse modelo:

- VPC com subnets públicas, privadas e de dados distribuídas em duas zonas de
  disponibilidade;
- cluster EKS e managed node group da aplicação nas subnets privadas;
- capacidade mínima, desejada e máxima configurável por ambiente;
- `metrics-server`, usado pelos HPAs de CPU;
- chart Helm da baseline com Deployments separados para `tracking-api` e
  `tracking-worker`;
- `topologySpreadConstraints` por `topology.kubernetes.io/zone`, para evitar a
  concentração dos pods de um mesmo workload em uma única zona quando houver
  capacidade disponível.

Os HPAs são materializados pela automação de deployment do backend, não pelo
chart deste repositório. A infraestrutura fornece os recursos estáveis,
`metrics-server`, nomes de contrato e Deployments necessários; a action do
backend aplica os HPAs `autoscaling/v2`, atualiza a imagem e ativa as réplicas
mínimas de cada workload.

Em produção, o perfil de capacidade mantém dois nós mínimos em On-Demand e
permite expansão até o limite configurado no `prod.tfvars`. Ambientes `dev` e
`hml` preservam a mesma topologia lógica, mas podem operar com menos nós e
menor redundância simultânea para controlar custo.

## Alternativas consideradas

### Amazon Elastic Container Service (ECS)

O ECS executaria os contêineres com menor carga operacional de Kubernetes e
poderia usar Fargate ou capacity providers. Foi recusado para este projeto
porque a plataforma já adotou Kubernetes como contrato operacional na ADR-001 e
precisa padronizar Deployments, probes, recursos, políticas de segurança,
distribuição por zona e HPA usando APIs Kubernetes.

### AWS Lambda

O Lambda ofereceria escala sob demanda e reduziria a gestão direta de compute.
Foi recusado porque a aplicação combina uma API contínua com workers de longa
duração, conexões persistentes com Redis e banco de dados, processamento de
fila e controle explícito de concorrência. Esse perfil favorece pods
long-running com rollout, recursos, probes e escalabilidade controlados no
cluster.

## Consequências

**O que esta decisão facilita:**

- Escala independente para API e workers, com limites e metas adequados a cada
  workload.
- Distribuição dos pods entre zonas de disponibilidade quando a capacidade do
  cluster permitir.
- Reuso das APIs Kubernetes para rollout, health checks, segurança, recursos e
  observabilidade.
- Separação clara entre infraestrutura estável, mantida neste repositório, e
  ativação da aplicação, mantida pela automação do backend.

**O que esta decisão dificulta:**

- Mantém custo fixo do control plane EKS e dos nós mínimos.
- Exige operação de Kubernetes, add-ons, capacidade dos node groups e métricas
  necessárias para o HPA.
- O HPA escala pods, mas não aumenta sozinho a capacidade de nós além do
  managed node group configurado; falta de capacidade deve ser tratada por
  ajuste de sizing ou por uma decisão futura de cluster autoscaling.
- Ambientes econômicos com um único nó não garantem redundância simultânea de
  pods entre zonas, mesmo que a rede seja Multi-AZ.

Esta decisão deverá ser revisitada se o custo operacional do EKS superar os
benefícios, se a volumetria passar a exigir autoscaling de nós mais sofisticado
ou se ECS/Lambda passarem a atender aos mesmos requisitos de disponibilidade,
controle de concorrência, distribuição zonal e padronização operacional.
